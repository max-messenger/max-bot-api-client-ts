# Showcase-бот и сквозные сценарии

Файл [`examples/showcase-bot.ts`](../examples/showcase-bot.ts) — бот для
проверки возможностей SDK для реализации многоступенчатых сценариев. Он не является
шаблоном production-архитектуры: профили и заказы хранятся в `Map` и пропадут после
перезапуска процесса.

## Запуск

```sh
npm run build
BOT_TOKEN=your-token npx tsx examples/showcase-bot.ts
```

`tsx` можно установить в проект приложения или запустить через `npx`; зависимость
намеренно не добавлена в SDK. Пример также проверяется компилятором при `npm test`.

Для быстрой проверки истечения состояния можно уменьшить TTL:

```sh
SHOWCASE_SESSION_TTL_MS=5000 SHOWCASE_SCENARIO_TTL_MS=5000 \
BOT_TOKEN=your-token npx tsx examples/showcase-bot.ts
```

## Что показывает пример

- `ctx.state` хранит `requestId` только в пределах одного update;
- `setMyCommands()` регистрирует подсказки, которые MAX показывает при вводе `/`;
- `session()` хранит корзину и прогресс сценария между update;
- `MemorySessionStore` удаляет неактивную сессию после TTL;
- `ScenarioEngine` ведёт два независимых named-step сценария;
- глобальные команды работают внутри активного сценария благодаря раздельным
  `controllerMiddleware()` и `interceptMiddleware()`;
- inline-кнопки, callback, запрос контакта и геопозиции обрабатываются как обычные
  шаги сценария;
- HTML-хелперы форматируют ответы, а пользовательское имя экранируется;
- ошибка финального шага не завершает checkout: пользователь может повторить
  сохранение с тем же стабильным идентификатором заказа;
- обновления одной сессии локально сериализуются, поэтому параллельные нажатия не
  теряют изменения корзины в пределах одного процесса.

## Сценарий 1. Базовый pipeline и сессия

1. Откройте бота или отправьте `/start` и проверьте короткое приветствие.
2. Отправьте `/help` и проверьте список команд.
3. Отправьте `/state`: `seenUpdates` увеличивается на каждом update, корзина пуста.
4. Отправьте произвольный текст и получите fallback-ответ.
5. Снова отправьте `/state` и убедитесь, что счётчик сохранился.

Проверяются middleware pipeline, update-scoped `state`, persistent `session` и
fallback-обработчик.

## Сценарий 2. Регистрация

1. Отправьте `/register`.
2. На запрос имени отправьте пустое/неподходящее сообщение и проверьте, что шаг не
   меняется.
3. Отправьте имя с символами `<`, `>` или `&`: в итоговом HTML оно должно показаться
   как текст, а не разметка.
4. Поделитесь контактом и геопозицией системными кнопками.
5. На экране подтверждения выберите «Изменить», пройдите шаги повторно, затем
   «Сохранить».
6. Отправьте `/profile` и проверьте сохранённые данные.
7. Отправьте `/state` и убедитесь, что поле `scenario` исчезло.

Проверяются типизированные данные шагов, `stay`/`goto`/`complete`, вложения,
callback и безопасное форматирование пользовательского ввода.

> Кнопки запроса контакта и геопозиции следует проверять в личном чате и в клиенте
> MAX, который поддерживает эти системные действия. Если браузерный клиент не
> открывает запрос геопозиции, кнопка «Использовать тестовую геопозицию» отправляет
> в сценарий тестовые координаты.

## Сценарий 3. Глобальные команды и отмена

1. Запустите `/register` и дойдите до любого промежуточного шага.
2. Отправьте `/help`: справка должна открыться, а регистрация — остаться активной.
3. Проверьте активный шаг через `/state`.
4. Отправьте `/cancel`, затем `/state`: активного сценария больше нет.

Так проверяется порядок middleware: глобальные команды стоят между установкой
контроллера и перехватчиком активного сценария.

## Сценарий 4. Корзина и checkout

1. Отправьте `/catalog`.
2. Несколько раз быстро нажмите кнопки разных товаров.
3. Нажмите «Показать корзину» или отправьте `/cart`: количества и сумма должны
   соответствовать всем нажатиям.
4. Нажмите «Оформить заказ» в корзине (или отправьте `/checkout`), выберите доставку.
5. Нажмите «Назад», смените способ получения и оформите заказ.
6. Проверьте через `/orders`, что заказ появился ровно один раз, и через `/cart`,
   что после успешного оформления корзина пуста.

Checkout делает snapshot корзины в данных сценария. Изменить обычными
catalog-callback его нельзя: активный диалог перехватывает такие update.

## Сценарий 5. Ошибка и безопасный повтор

1. Добавьте товар и отправьте `/checkout`.
2. Выберите способ получения.
3. До нажатия «Оформить» отправьте глобальную команду `/fail_next_order`.
4. Нажмите «Оформить»: бот сообщит о тестовой ошибке.
5. Отправьте `/orders`: новый заказ ещё не должен появиться.
6. Отправьте `/state`: сценарий всё ещё находится на шаге `confirm` с тем же
   `orderId`.
7. Нажмите «Оформить» повторно: заказ сохранится, а сценарий завершится.
8. Снова отправьте `/orders`: заказ должен присутствовать в единственном экземпляре.

Scenario применяет переход только после успешного завершения шага. Стабильный
`orderId` позволяет repository выполнить идемпотентную запись при повторной доставке
update. Настоящий бот должен обеспечивать такую гарантию в своей базе данных.

## Сценарий 6. TTL

1. Запустите бот с обоими TTL, равными `5000` мс.
2. Начните `/register` и не отправляйте ничего более пяти секунд.
3. Отправьте имя. Сессия уже истекла, поэтому сообщение попадёт в fallback, а не в
   старый шаг.
4. Запустите `/register` ещё раз — сценарий начнётся с начала.

Session TTL очищает всю in-memory сессию. Scenario TTL нужен отдельно, когда
durable session живёт дольше самого пользовательского сценария.

## Границы примера

`MemorySessionStore`, `Map` профилей и `Map` заказов подходят только для локального
стенда или одного процесса. Один экземпляр может сохранять сессии в SQLite.
Нескольким экземплярам нужны общие хранилища: например, Redis для сессий и
блокировок, PostgreSQL для профилей/заказов и уникальный индекс по `orderId` для
идемпотентности. SDK управляет порядком обработки, но бизнес-транзакции и
согласованность нескольких процессов остаются ответственностью приложения.
