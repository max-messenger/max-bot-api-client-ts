# `9` Концепция SDK

## Модель выполнения

SDK разделяет работу бота на пять уровней:

```text
MAX API → Polling → Bot/Composer → Session → Scenario → бизнес-сервисы
                                      ↓              ↓
                                   Context       основная БД
```

1. Сетевой слой получает update и преобразует ошибки API в `MaxError`.
2. `Bot` создаёт новый `Context` и запускает onion-цепочку middleware.
3. `session()` загружает состояние пользователя и сохраняет его после цепочки.
4. `ScenarioEngine` при необходимости направляет update в активный сценарий.
5. Бизнес-код использует `ctx.api`/`ctx.reply`, а постоянные сущности сохраняет в
   собственной базе данных.

## Время жизни данных

| Данные | Где находятся | Время жизни |
|---|---|---|
| Текущий update, match, вычисленная роль | `Context` и `ctx.state` | один update |
| Текущий экран, черновик формы, счётчик | `ctx.session` | несколько update |
| Шаг регистрации или оформления заказа | `session.scenario` | до завершения/TTL |
| Пользователь, корзина, заказ, остатки | база приложения | независимо от процесса бота |

Session и scenario не являются бизнес-БД. Они хранят только небольшой
serializable state, необходимый для продолжения общения.

## Сетевой и API-слой

`core/network/api` содержит HTTP client, raw API, DTO и модули bots, chats,
messages, subscriptions и uploads. Этот уровень повторяет контракт MAX API и не
знает о middleware или сценариях.

`Api` предоставляет удобные методы верхнего уровня: отправку и редактирование
сообщений, работу с чатами, callbacks, actions и upload. `Context` делегирует ему
операции, для которых идентификатор уже можно получить из текущего update.

`Polling` запрашивает update, хранит marker и передаёт каждый update в `Bot`.
`Bot` создаёт отдельный `Context`, запускает middleware и передаёт исключения в
настроенный обработчик `catch`.

## Core и Composer

Middleware получает `(ctx, next)`. Вызов `next()` передаёт управление следующему
обработчику, а код после `await next()` выполняется на обратном пути. Это даёт
middleware возможность подготовить данные до обработчика и сохранить/очистить
их после него.

`Composer` — публичный фасад цепочки. Его внутренние модули лежат в
`core/composer/modules`:

- `composition.ts` строит onion-цепочку и условные ветви;
- `triggers.ts` нормализует command/hears/action;
- `dispatch.ts` выбирает именованный маршрут и безопасно дополняет `ctx.state`;
- `filters.ts` проверяет тип события и подсказывает TypeScript, какие поля доступны;
- `context.ts` предоставляет данные update и удобные методы ответа.

`Bot` наследует `Composer`, поэтому все операции Composer доступны непосредственно
на экземпляре бота.

## Session

`session()` вычисляет ключ, загружает значение из `SessionStore`, добавляет его в
Context и сохраняет в `finally`. Присваивание `null` или `undefined` удаляет
session. Update без пары `user_id`/`chat_id` по умолчанию проходит без session.

`KeyedExecutor` последовательно выполняет update одного ключа внутри процесса,
но не задерживает других пользователей. `MemorySessionStore` клонирует значения
и поддерживает TTL; он предназначен для разработки и временного запуска. После
остановки или перезапуска процесса все его сессии и незавершённые сценарии
пропадут.

Для одного процесса сохраняемое состояние можно хранить в SQLite. В multi-replica
окружении нужен общий `SessionStore`, например Redis или серверная база данных.
Атомарное обновление или блокировку одного ключа должен обеспечить адаптер или
инфраструктура: простые `get/set/delete` не координируют разные процессы.

## Scenario

Definition описывает конечный автомат с именованными шагами. Каждый шаг получает
неизменяемый snapshot и возвращает ровно один переход:

- `stay(patch)`;
- `goto(step, patch)`;
- `complete()`;
- `cancel()`.

Переход применяется только после успешного шага. При исключении прежний state
остаётся доступным для повтора. TTL является sliding: успешный `stay/goto`
обновляет deadline.

Короткое подключение подходит, когда активный сценарий должен получать все update:

```typescript
bot.use(session());
bot.use(scenarios);
```

Раздельное подключение оставляет место для глобальных команд:

```typescript
bot.use(session());
bot.use(scenarios.controllerMiddleware());
bot.help(helpHandler);
bot.command('cancel', cancelHandler);
bot.use(scenarios.interceptMiddleware());
```

Controller сообщает `active/current`, запускает definition и отменяет активный
сценарий. `definition.intercept` обрабатывает команды, специфичные для одного
definition, а затем ScenarioEngine запускает текущий шаг.

## Helpers

Attachments и buttons строят модели запросов MAX API. `Keyboard.inlineKeyboard`
преобразует готовую сетку кнопок во вложение. `fmt` формирует Markdown/HTML;
пользовательский текст необходимо передавать через `escape`/`escapeHtml`.

`Upload` получает URL загрузки, нормализует путь/stream/Buffer и отправляет файл
подходящим для его типа способом. Он не управляет сценарием и возвращает данные,
из которых `Api` строит attachment.

## Что даёт расширенный SDK

Раньше SDK умел получать update, фильтровать базовые события и вызывать MAX API.
Сложный stateful-бот был возможен только после собственной реализации session,
маршрутизатора, блокировок и конечного автомата в каждом проекте.

Теперь на общих примитивах можно строить:

- регистрацию с подтверждением телефона и повтором невалидного шага;
- корзину и checkout с выбором адреса, доставки и подтверждением заказа;
- бронирование переговорной или услуги с выбором слота;
- onboarding сотрудника с разными ветками по роли;
- опросы, квизы и экзамены с сохранением прогресса;
- службу поддержки с категоризацией и сбором вложений перед созданием заявки;
- согласование заявки несколькими ролями через `dispatch`;
- настройку уведомлений и многошаговые административные формы.

Бизнес-сущности в этих ботах остаются в БД приложения. Scenario хранит лишь
позицию пользователя и черновик, а финальный шаг вызывает идемпотентный
бизнес-сервис.

## Что важно учитывать

- Сессия и основная база данных сохраняются отдельно. Одно событие может прийти
  повторно, поэтому используйте уникальный идентификатор, чтобы не создавать
  дубликаты.
- Встроенное хранилище работает только внутри одного процесса. После перезапуска
  бота его данные пропадут.
- Для одного экземпляра можно использовать SQLite; нескольким экземплярам нужно
  общее хранилище, например Redis или серверная база данных.
- Пошаговые сценарии управляют общением с пользователем, но не заменяют очередь
  задач и операции с базой данных.
- Перед добавлением пользовательского текста в HTML или Markdown используйте
  `escapeHtml()` или `escape()`.

SDK отвечает за обработку сообщений и шаги сценария. Способ хранения постоянных
данных приложение выбирает самостоятельно.
