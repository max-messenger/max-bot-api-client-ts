# `8` Архитектура диалогов

## Область ответственности

Conversation — тонкий слой маршрутизации поверх session. Он отвечает только за:

- идентификатор активного сценария;
- именованный текущий шаг;
- временные данные формы;
- необязательный inactivity timeout.

Пользователи, корзины, остатки и заказы остаются в основной БД.

Conversation middleware можно подключить двумя способами. `middleware()` —
совместимый короткий путь, сразу добавляющий controller и перехватывающий
активный сценарий. Раздельные `controllerMiddleware()` и
`interceptMiddleware()` оставляют между этими фазами место для глобальных
команд. Они полезны для `/help`, `/cancel` и административных проверок, которые
не должны дублироваться в каждом definition.

## Почему состояние находится в session

Состояние диалога хранится в обычной сессии. Отдельное хранилище только усложнило бы настройку и могло привести к расхождению данных.
В одном запущенном боте сообщения одного пользователя обрабатываются по очереди.
Если бот работает в нескольких экземплярах, согласованность данных должно обеспечивать общее внешнее хранилище, например Redis или база данных.

## Завершение и ошибки

Engine применяет transition только после успешного выполнения шага. Поэтому
ошибка оставляет предыдущий шаг доступным для повторной обработки.

Критическую операцию выполняйте до `transition.complete()`:

```typescript
await orders.create({ idempotencyKey, cartId });
return transition.complete();
```

Одно событие может быть обработано повторно. Используйте уникальный идентификатор, чтобы не создавать дубликаты в базе данных.
