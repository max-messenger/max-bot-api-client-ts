# `8` Архитектура диалогов

## Область ответственности

Conversation — тонкий слой маршрутизации поверх session. Он отвечает только за:

- идентификатор активного сценария;
- именованный текущий шаг;
- временные данные формы;
- необязательный inactivity timeout.

Пользователи, корзины, остатки и заказы остаются в основной БД.

Conversation middleware можно подключить двумя способами. `middleware()` —
совместимый короткий путь, сразу добавляющий controller и перехватывающий
активный сценарий. Раздельные `controllerMiddleware()` и
`interceptMiddleware()` оставляют между этими фазами место для глобальных
команд. Они полезны для `/help`, `/cancel` и административных проверок, которые
не должны дублироваться в каждом definition.

## Почему не Stage и Wizard

Числовой cursor зависит от порядка функций в массиве. Именованный шаг сохраняет
смысл при добавлении новых шагов:

```text
collect-name → collect-phone → confirm
```

`transition.goto('confirm')` явно показывает изменение состояния. Отдельные
`Stage`, `BaseScene`, `WizardContext` и `Router` для этого не нужны.

## Почему состояние находится в session

Отдельный conversation store дублировал бы ключи, TTL, подключение внешнего
хранилища и модель конкурентности session. Единственная точка сохранения проще и
не допускает рассинхронизации двух stores.

Внутри одного процесса session последовательно обрабатывает update одного ключа.
При нескольких replica гарантии предоставляет внешний адаптер или архитектура
приложения; in-memory SDK не изображает распределённую транзакцию.

## Завершение и ошибки

Engine применяет transition только после успешного выполнения шага. Поэтому
ошибка оставляет предыдущий шаг доступным для повторной обработки.

Критическую операцию выполняйте до `transition.complete()`:

```typescript
await orders.create({ idempotencyKey, cartId });
return transition.complete();
```

Exactly-once между session store и бизнес-БД невозможен без общей транзакции.
Обработчики записи должны поддерживать идемпотентный ключ.

## Происхождение реализации

API реализован независимо на основе общих примитивов middleware и конечного
автомата. Код `Stage/Scene/Wizard` из других SDK не переносился. Репозиторий
MAX SDK распространяется под MIT; его текст лицензии остаётся в корне проекта.

Go-клиент MAX проверялся только на наличие относящихся к задаче session/dialog
механизмов. Таких механизмов в нём нет, поэтому его код здесь не использован.
